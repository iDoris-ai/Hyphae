# 社交协议草案

状态:草案,未冻结。kind 编号、tag、加密方式都不在本文决定,要走 [T01 契约收口](../agent/t01-contract-gates.md)。本文只定义 `content` 里的 JSON 和状态机。

## 共同约定

- 每条消息是一个 Nostr 事件。作者取自**验签通过的事件公钥**,正文里不放作者字段,也不能覆盖它。
- 消息之间用**事件 ID** 互相引用。不另造摘要算法,事件 ID 已经是规范化的哈希。
- 正文是 JSON 对象,必有 `v`(整数,当前为 1)和 `type`(字符串)。
- 解析规则:未知版本拒绝;未知字段拒绝;重复的 key 拒绝;正文超过 16 KiB 拒绝;嵌套超过 16 层拒绝。
- 所有 JSON key(包括 `fields` 里的)只能用 `a-z`、`0-9` 和下划线,长度 1–32。原因:有的 JSON 库匹配字段名不区分大小写,`Offer` 会被当成 `offer`;限制 key 的写法后,各语言的实现对"正文里有哪些 key"才有一致的结论。
- 公钥和事件 ID 都是 64 位小写十六进制。
- 时间是 Unix 秒。
- 字符串必须是合法的 Unicode。未配对的代理项转义和非法字节一律拒绝;为了让各语言的实现结论一致,含有替换字符 U+FFFD 的字符串也拒绝。
- JSON 里不允许出现 `null`。协议里没有可空字段,可选字段不写就是没有。
- **事件时间是发送方自己填的,不可信**。凡是"过期"这类判断,都用本地观察到这条消息时的时钟,不用消息里的时间。调用方要把每条消息的观察时间存下来,重建状态时原样传回。
- 消息时间比本地时钟超前**超过** 300 秒的,先搁置,不算拒绝,等时钟追上再处理。正好超前 300 秒的照常处理。
- relay 不保证顺序,所以拒绝分两种:
  - **本身就不对**的消息(格式错、引用了别的意图或请求、作者是局外人、时间写在过期之后):每次投递都得到同样的拒绝。
  - **只是时机未到**的消息(比如回执比它引用的接受消息先到):不记为拒绝,返回"现在不行"。调用方把它留着(每个会话留的数量要有上限),等下一条消息处理完再试一次。
- 不同作者的时钟不可比,所以不用事件时间给不同作者的消息排先后,先后由状态机决定。
- 上面说的"超前 300 秒先搁置"适用于所有入口:建立会话、建立引荐流程、解析邀请链、计算信誉分。
- 这些消息**都不构成执行授权**。它们属于"查询/通知"一类,不会让对方 agent 启动任何有副作用的任务。

代码里用 `social.Envelope` 表示"已验签事件的投影":`ID`、`Author`、`CreatedAt`、`Content`。纯逻辑包只接收 `Envelope`,不碰 relay 和签名。

## 一、意图(方向 1)

包:`internal/social/intent`

### 消息

| type | 可见性 | 字段 |
|---|---|---|
| `intent` | 公开 | `category`、`summary`、`window`、`area`、`party`、`expires_at` |
| `respond` | 私密,发给意图作者 | `intent`(事件 ID)、`fields` |
| `disclose` | 私密 | `intent`、`round`、`fields` |
| `accept` | 私密 | `intent` |
| `decline` | 私密 | `intent`、`reason`(可选) |
| `withdraw` | 公开 | `intent` |

字段约束:

- `category`:小写短字符串,如 `meal`、`date`。长度 1–32,只含 `a-z0-9-`。
- `summary`:1–280 个字符,不能只有空白。
- `window`:`{from, to}`,`0 < from < to`。
- `area`:粗粒度地点,1–64 个字符,不能只有空白。不放精确坐标。
- `party`:`{min, max}`,`1 ≤ min ≤ max ≤ 20`。
- `expires_at`:晚于事件时间,最多晚 30 天。
- `fields`:字符串到字符串的映射,1–16 项,key 遵守共同约定里的 key 规则,value 最多 512 个字符。正文总长仍受 16 KiB 限制:16 项都写满 512 个汉字约 24 KiB,会先被正文上限拒绝。

### 状态机

一个会话由"意图 + 响应方公钥"确定。意图作者是 A,响应方是 B。

```
Open ──respond(B)──▶ Responded ──disclose 交替──▶ Disclosing
                                                    │
                          accept(A) + accept(B) ────┴──▶ Matched
任何一方 decline ──▶ Declined
A withdraw ──▶ Withdrawn
超过 expires_at ──▶ Expired
```

规则:

- 公开的 `intent` 本身算 A 的第 0 轮披露,`respond` 算 B 的第 0 轮披露。所以 `respond` 之后双方都可以发第 1 轮。
- 披露必须**交替**:一方发了第 n 轮,要等对方也发了第 n 轮,才能发第 n+1 轮。这样谁也不能只收不给。
- 最多 5 轮,即第 0–4 轮;`disclose` 的 `round` 只能是 1–4。
- `respond` 和 `disclose` 的 `fields` 不能为空,否则一方可以什么都不给就推进轮次。
- `respond` 之前不能 `accept` 或 `decline`。任何一方 `accept` 之后,双方都不能再 `disclose`。
- 先确认消息作者是 A 或 B,再判断是否过期。局外人发一条时间写得很晚的消息,不能让会话提前过期。
- 只有双方都发了 `accept` 才算 Matched(双向同意)。单方 `accept` 不向第三方泄露任何东西。
- Matched、Declined、Withdrawn、Expired 是终态,之后的消息一律拒绝。
- 事件时间晚于 `expires_at` 的消息拒绝。
- 作者不是 A 也不是 B 的消息拒绝。
- 已经生效的事件 ID 重复投递,不报错也不改状态。
- 只有本地时钟能让会话过期:时钟超过 `expires_at` 后会话记为 Expired,之后补发的、时间写在过期之前的消息不能让它复活。反过来,一条时间写在 `expires_at` 之后的消息只是它自己被拒绝,不会让会话提前过期。

匹配成功后把人拉进群,是上层用现有群聊功能做的事,不属于这个包。

## 二、信任(方向 2)

包:`internal/social/trust`

### 消息

| type | 可见性 | 字段 |
|---|---|---|
| `invite` | 公开 | `invitee`(公钥) |
| `invite_accept` | 公开 | `invite`(事件 ID) |
| `attest` | 由被背书人决定出示给谁 | `subject`(公钥)、`claim`、`value`、`expires_at` |
| `rating` | 公开 | `subject`(公钥)、`match`(两个 accept 的事件 ID)、`score`(1–5)、`tags`(可选) |

### 邀请链

事件时间是发送方自己填的,所以邀请链不靠时间先后判断谁先入链。改由**被邀请人自己选定邀请人**:

- 新增消息 `invite_accept`,由被邀请人签发,字段 `invite`(邀请的事件 ID)。
- 有一组配置好的**根**公钥。根没有邀请人,根签的 `invite_accept` 一律忽略。
- 一个身份的邀请人由它自己决定:在它签的、指向"确实发给它的邀请"的 `invite_accept` 里,取时间最早的一条(时间相同按事件 ID 排),那条邀请的作者就是它的邀请人。指向不存在的邀请或发给别人的邀请的,直接忽略。别人无法设定或改变它的邀请人。
- 每个身份最多邀请 N 个(默认 6):按事件时间排序只取前 N 条,时间相同按事件 ID 排。前 N 条每条都占名额,不管对方是否接受、是否是根。
- 如果一个身份选定的那条邀请排在邀请人的前 N 条之外,它就没有有效的邀请人,也不会退而求其次去用另一条。
- 一个身份有效,当且仅当它是根,或者沿着邀请人一路往上能在深度上限(默认 8)内到达根。根的深度是 0,处在深度上限的身份不能再做邀请人。
- 自己邀请自己无效。互相邀请成环的,因为到不了根,全部无效。
- 结果只取决于收到了哪些事件,和收到的顺序、是否重复无关。

已知的弱点:

- 邀请人可以事后补签几条时间更早的邀请,把某个人挤出前 N 名,让他和他的下级全部失效。只有邀请人本人做得到,等于一种不留痕迹的单方面撤销。
- 被邀请人可以补签一条时间更早的 `invite_accept` 改换邀请人,他的下级的深度会跟着变。
- 不同的观察者收到的事件不同,对同一个身份是否有效可能得出不同结论。
- `invite_accept` 是公开的,谁邀请了谁完全可见。
- 一个有效成员最多能带出约 6^8 个身份,这是名额和深度上限决定的。

### 背书

- 背书人签名说"这个公钥的某项属性是某个值",比如 `age_range = 25-30`。
- 选择性披露就是被背书人只把想出示的那几条背书事件转给对方。
- 字段约束:`subject` 不能是背书人自己;`claim` 遵守 key 规则;`value` 是 1–128 个字符,不能只有空白;`expires_at` 晚于事件时间,最多晚 366 天。
- 校验:背书人在本地信任的背书人名单里;`subject` 是出示人;按本地时钟没过期;事件时间没有超前本地时钟超过 300 秒。
- 同一个背书人对同一项 `claim` 只认最新的一条。不同背书人对同一项的结论都保留,由调用方决定怎么权衡。
- 一次最多出示 64 条。
- 已知的限制:没有撤销,只能等过期或由同一个背书人发新的覆盖;出示人可以不出示对自己不利的背书。

### 评价与信誉分

- 评价必须引用一次匹配:`match` 是双方 `accept` 的事件 ID。评价人和被评价人必须正好是这次匹配的双方。
- 一个评价人对一次匹配只算一条,取最新的。
- 一个评价人对同一个人的多次评价,合并成一个平均值再计入。这样刷单的收益有上限。
- 只有邀请链有效的评价人才计入。
- 分数用带先验的平均:`(先验分 × 先验权重 + Σ 评价) / (先验权重 + 评价人数)`,默认先验分 3、先验权重 5。新人不会因为一条五星就排到最前。

信誉分只能让撒谎变贵,不能证明信息为真。

## 三、引荐(方向 3)

包:`internal/social/referral`

### 消息

| type | 可见性 | 字段 |
|---|---|---|
| `referral_request` | 私密,发给引荐人 | `intent`(事件 ID)、`offer`(积分数)、`hops_left`、`expires_at` |
| `referral_forward` | 私密,引荐人发给目标或下一个引荐人 | `request`(事件 ID)、`intent`、`hops_left` |
| `referral_accept` | 私密,目标发出 | `forward`(事件 ID) |
| `referral_decline` | 私密 | `forward` |
| `receipt` | 公开 | `to`(公钥)、`amount`、`ref`(`referral_accept` 的事件 ID) |

### 规则

- **接受后才付费**。目标发了 `referral_accept`,请求人才欠最后一个引荐人 `offer` 个积分。转发本身不收费,所以乱转发没有收益。
- `hops_left` 初始最多 3,每转发一次减 1,到 0 不能再转发。
- 引荐人不能把请求转回给请求人,也不能转给自己。
- 状态:Requested → Forwarded → Accepted → Settled,或者 Declined、Expired。
- `receipt` 的作者必须是请求人,`to` 必须是最后一个引荐人,`amount` 必须等于 `offer`。同一个 `ref` 只认第一条。
- 目标只能接受或拒绝最近一次转发。转发给链上已经出现过的人无效。
- **已接受的引荐不会过期**,过期后的 `receipt` 仍然有效。否则欠款人拖到过期就能赖账。
- 过期按当前时钟判断,并且一旦过期就记下来。时间写在过期之前的补发消息不能让流程复活;时间写在未来的消息也不能让流程提前作废。

### 积分

- 积分是**不可交易的互助信用**,不是代币。第一版不上链,不接真实支付。
- 账本从 `receipt` 事件推导:每个身份的余额 = 收到的 − 付出的。
- 每个邀请链有效的身份有一个额度上限(默认 100)。占用额度的有三项:结算后的负余额、已接受但还没付的出价(不管是否逾期)、还在进行中的请求的出价。三项之和加上本次出价超过上限的,不能发起引荐请求。
- 付清一笔只是把"未付"变成"负余额",不释放额度。只有自己做引荐人赚到积分才能恢复额度。否则付款人自己出一张回执就能无限重置额度。
- 同一个请求在账本里只算一次,不管它被传入几次。传入多份时取处理过事件最多的那份,过时的一份盖不住已接受或已结算的状态。
- 逾期的宽限期从本地观察到接受消息的时间起算,不用目标自己填的时间。
- 求和不回绕,到整数上限就停在上限。
- 单笔积分上限 1,000,000。
- 已到 Accepted 但超过宽限期还没有 `receipt` 的,记为欠款,同样计入上限。

没有共同账本,每个观察者只能看到自己收到的事件,所以余额是"各自视角"的。这是第一版已知的限制,见下面的待定问题。

## 待定问题

1. kind 编号、tag、公开和私密消息各自的加密封装:交给 T01-A。
2. 外层路由信息对 relay 可见的问题(谁在跟谁说话):要不要换成隐藏收发双方的封装。
3. 积分账本的一致性:各自视角够不够用,还是需要一个大家都能查的地方。
4. 根公钥和信任的背书人名单由谁维护。
5. 评价的申诉和撤回。
6. 未成年人和诈骗的处置流程。
7. 邀请的显式撤销:现在邀请人只能靠补签旧时间的邀请来挤掉人,应该有一条正式的撤销消息。
8. 额度上限的默认值(100):现在进行中的请求也占额度,付清不释放,等有真实用户后需要再调。
