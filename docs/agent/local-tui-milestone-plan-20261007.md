## 交付顺序与验收标准

1. **本批反馈修复。** Hyphae 负责 #26/#27/#129/#130/#131；发布基础测试结果与 PR，交 PR-Daemon review。#27 合并并由 Agent24 升级锁定版本后，才进入 COMM7。macOS Python 3.14.7 的 50 次 CI 回归成功前，不宣称 #130 的指定 CI 出口完成。
2. **P0：本地两至三用户点对点 TUI 实时闭环。** 用户已授权优先完成 M1，先确定 TUI 使用已有接收组件还是管理自有 daemon，再由 Luna 实现。复用现有解密、签名校验、SQLite event-ID 去重，不另建第二套收件协议；界面线程不得阻塞网络，退出只停止自身拥有的工作进程。断线/重连与失败状态可见，relay ACK 不冒充对方已读/已展示。
   - 三份隔离身份可注册、互相发现、建立联系人；不依赖公网 relay。
   - 三组用户组合均双向发送，接收方保持 TUI 打开即可看到消息；建议本地健康网络验收目标为落库后 2 秒内刷新，实施前冻结该阈值。
   - 重启保留历史；重放同一事件不重复；离线后重连补收；错误不展示为成功。
   - 自动化真实 relay + PTY 测试验证发送、接收落库与接收界面文本三段；另做人工键盘/退出体验验收。
   - 最终交付一条本地 relay 启动命令和明确的两/三用户启动指南；独立 daemon 若仍必需必须写明。
3. **M1 群聊与关闭验收。** 先冻结成员/密钥/广播/历史/UI 最小规格，再做三个用户保持 TUI 打开的实际群消息收发、去重和重启历史。离群后的权限与历史边界必须明确；不以 group create/list 充当完成证据。安全或协议选择若需要用户决策，先报告，不猜测。
4. **Agent24 COMM6b→COMM7。** M1 完成后推进。Agent24 负责配置、会话/历史/发件箱界面和 production lock 更新；Hyphae 提供稳定协议与联调 CI。先通过 #27 门槛，再做真实桌面收发/重试；衍生 candidate lock 的 CI 通过不代替生产锁升级。
5. **M2 与 E-M1 执行出口。** M1 完成后，先消解现有行为 kind 文档冲突、冻结信封和兼容策略，再实现基础行为；执行契约/授权门槛明确后，验证一次授权请求→执行→回执。避免把聊天问题留到执行链路之后。
6. **M2.5→M3→M4→M5。** 分别以跨 relay、任务恢复、长期运行、资金安全为出口；每阶段通过后才排下一阶段。当前不承诺未经验证的日历工期。

三用户点对点不等于三人群聊。群聊需要明确成员/密钥/广播/历史/UI 的独立规格，不能用 group create/list 充当完成证据。
