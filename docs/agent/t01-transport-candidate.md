## 存储与命名空间

建议新的行为请求、回执及公开声明共用 regular kind `8787`，用 `c=hyphae-behavior/1` 区分应用协议，用 `b` 区分行为。编号是实验候选，不是 NIP 分配或全生态保留。2026-09-30 核对 [NIP 列表](https://github.com/nostr-protocol/nips/blob/master/README.md) 和 [kind registry](https://github.com/nostr-protocol/registry-of-kinds/blob/master/schema.yaml) 未发现 8787；登记表不完备，命名空间检查仍必需。

这个选择让请求和回执按事件 ID 分别保留。资料声明也保留历史，客户端选择同作者的最新有效声明；不另引入 profile kind。新声明的排序、失效及注册字段由 T01-B 固定，不能在这里自行猜测。同时间冲突要有确定规则；过期的最新声明不能让旧能力自动重新生效。

现有 profile 仍按 kind `30078`、`d=agent-profile`、`c=profile` 读取。新请求不能写到这个地址，不能将 profile 当执行请求。旧记录不做静默转换。

[NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md) 定义 regular 和 addressable 的不同保留语义；同作者、kind、`d` 的 addressable 新记录可能替换旧记录。`b` tag 不改变这个地址。因此只在旧 30078 上增加行为名，无法证明多个请求及回执会被分别保留。

[NIP-78](https://github.com/nostr-protocol/nips/blob/master/78.md) 将 78/30078 用于应用私有存储，建议认证并仅向事件作者提供读取；它不推荐把这些 kind 作为跨应用公开交换格式。现有 profile 在本生态 relay 的历史兼容可以继续验证，但不能保证任何公共 relay 都允许他人发现这些记录。新公开声明需用专用交换协议并实际探测所选 relay 的能力。

## 公开与点对点编码

| 场景 | 外层 tags | content 候选格式 |
|---|---|---|
| 公开 register、publish | 唯一 `c`、`b`、`x=json`；不带目标 `p` | UTF-8 JSON 文本，只包含明确允许公开的字段 |
| 点对点查询、执行请求、回执 | 唯一 `c`、`b`、`x=nip44`、目标 `p` | NIP-44 v2 加密 UTF-8 JSON，输出使用标准带 padding 的 Base64 |
| 点对点回执/查询响应 | 上述点对点 tags，另带唯一 `e` 指向原请求事件 | 密文中的请求 ID、目标和关联事件与外层一致 |

`c` 固定为 `hyphae-behavior/1`。`b` 的允许值和消息类型组合在 T01-B 表中固定；识别行为名不授予执行权限。`x` 是本应用的编码声明，不假定其他 Nostr 应用使用同一含义。

点对点目标、公钥和事件 ID 使用 64 字符小写十六进制。可读显示名称、npub 和正文里的身份都不能替代签名作者。查询响应及执行回执必须由原请求目标签名，并投递给原请求作者；第三方不能通过同一个 request_id 更新请求状态。

候选首次版本直接加密 JSON，不添加 zstd 或旧 `agent:VERSION:zstd:` 前缀。旧消息的压缩读取仍走旧消息入口。未来如增加压缩，需新编码协商、解压资源限制及跨语言样例，不能由接收方盲试多种格式。

NIP-44 加密保护正文；外层作者、目标、行为 tag、时间和事件大小仍可见。需要隐藏通信关系时另行设计封装，不能把这个候选描述为隐藏元数据。

## 有界输入与校验顺序

以下是应用候选上限，须在固定 Go 与 Agent24 实现之间验证，不能称为 NIP 的永久限制。

| 对象 | 候选上限 | 拒绝时机 |
|---|---|---|
| 单个事件 JSON | 64 KiB UTF-8 字节 | 事件反序列化前；网络帧限制另外规定 |
| 解密前的 content | 44 KiB ASCII 字节 | Base64 解码和密钥计算前 |
| 公开正文/解密后正文 | 32 KiB UTF-8 字节 | JSON 解析前 |
| tags | 最多 8 项，每项最多 3 个字符串，每个字符串最多 256 UTF-8 字节 | 验签及内容解析前 |
| 正文 JSON | 最大嵌套 16 层 | 受限解析时；数字、重复 key、未知字段策略由 B 固定 |

正文边界按字节判断，不按字符数。所有关键 tag 均要求存在、唯一、值和长度合法；重复值相同也拒绝。未知协议版本、编码或关键 tag 不退回普通消息执行路径。保留可诊断错误，不自动改写输入。

处理顺序：限制原始输入 → 解析最小事件结构和 tags → 核对 kind/命名空间/编码/目标 → 验证事件 ID 和签名 → 有界解密 → 校验正文结构、版本及外层一致性 → 登记接收。进入 Agent24 执行前，还须完成能力、摘要、授权、有效期、预算、持久化去重和 run 核对。

网络限制要考虑 `EVENT` 信封额外字节，不能把整个 WebSocket 帧直接等同于单个事件 JSON。继承当前查询层的帧上限不等于完成新的正文校验。

32 KiB 明文经 NIP-44 小长度前缀及 padding 后，Base64 payload 应在 44 KiB 候选上限内；由固定 SDK 实测确认，接收端仍检查解密后的独立上限。最新版 [NIP-44](https://github.com/nostr-protocol/nips/blob/master/44.md) 允许实现自设资源限制；固定 SDK 的边界与标准变化分别记录。

固定 SDK 的 `nip44.Decrypt` 在最小长度检查后直接 Base64 解码，没有最大输入限制；新的接收入口须先执行本表上限。其 MAC 比较当前使用 `bytes.Equal`，而 NIP-44 要求常数时间比较；这项上游符合性差异需另行评审与适配，不能用同库加解密回环声明全部安全要求已通过。

## 兼容矩阵

| 输入 | 读取/展示 | 执行入口 |
|---|---|---|
| 当前 CLI 30078 消息与压缩正文 | 沿用旧消息路径及其身份/历史语义 | 不因内容看似新 JSON 而执行 |
| 30078 profile | 沿用 profile 路径；注明所用 relay 的读取策略 | 不执行 |
| 普通文本、Agent24 `f4/1`，包括 answer | 通信展示；保持原格式 | 不执行 |
| 新 kind 但缺失/不同命名空间 | 不作为本协议解析 | 不执行 |
| 正确命名空间、未知版本/编码/行为 | 返回不支持或保留供诊断 | 不执行 |
| 有效查询、声明、订阅通知、回执 | 按对应协议类型登记或展示 | 不启动 run |
| 合法执行请求 | 交给 Agent24 授权与持久化执行登记 | 获授权且全部前置通过后才可启动 run |

新 CLI 通信服务应独立识别事件类别。现有 watcher 的 30078 过滤器不会自动接收新 kind；T08/T09 必须增加明确的过滤、恢复和持久化路径，不能仅新增序列化函数便宣称已接通。
