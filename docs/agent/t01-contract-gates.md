## 当前需要解决的冲突

`protocol-v2.md` §4 将行为放在 kind 30078；`spec.md` 要求独立 kind，却没有编号。这两段均不能直接作为新实现的完整契约。T01 收口时一起修改，权威定义仍放在 `protocol-v2.md`；速查文档只引用同一字段表。

Nostr 的 kind 决定 relay 的保留方式：regular 事件可分别保留；30000～39999 属于 addressable，同一作者、kind、`d` 的新事件可替换旧事件。因此资料快照与请求/回执需要分别决定存储语义，不能只把 behavior 写进 `b` tag 就认为它们独立保存。依据：[NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md)。

设计建议是：请求与回执使用一个明确命名空间的 regular kind，通过受约束的消息类型区分；资料快照沿用经核对的 profile 存储语义。具体编号需核对 NIP 列表、固定版本 SDK 和真实 relay，再随共享样例冻结；不为每个动词分配 kind。尚未冻结前，保留旧 30078 的读取路径，不将其猜测为新的可执行请求。

## T01-A 必须固定的细节

- 公钥与事件 ID 的编码和长度；签名、事件 ID、接收者过滤由哪个入口验证；正文不能覆盖签名作者。
- 哪些 tag 必填且唯一，如何处理重复、未知或正文不一致的 tag。即使密文隐藏正文，也要明确外层路由字段会暴露的信息。
- 公开资料与点对点请求分别怎样编码、加密。协议解析与普通消息展示使用不同入口；解密失败不退回明文执行。
- 在验签前限制事件字节数；解密前限制密文字节数；如使用压缩，还要限制解压输出、内存和时间。限制值须来自固定 Go/TypeScript 实现的互操作测试。
- 不把旧 SDK 的长度边界写成 NIP-44 的永久限制。应用应选择自己的有界大小，并测试边界内、边界外、截断和无效编码。标准依据：[NIP-44](https://github.com/nostr-protocol/nips/blob/master/44.md)。
- 旧 30078、普通文本、Agent24 `f4/1`、新信封、未知版本各有独立处置。兼容读取不等于兼容执行；无效输入不能被“修复”为授权请求。

## T01-B/C 字段与责任

下列是必须覆盖的语义；最终 wire 字段名、枚举和格式在 B/C 的权威表中固定。

| 信息 | 来源与约束 | 负责方 |
|---|---|---|
| 发送者、目标身份 | 发送者来自验证通过的签名；目标必须与路由及当前接收身份一致 | Hyphae 验证，Agent24 再检查授权 |
| 协议版本、消息类型 | 查询、通知、执行请求、回执分开；开放 intent 不能授予执行权限 | 共同契约 |
| request_id、关联事件 | 请求 ID 跨发送重试稳定；回执指向原请求，不能仅凭 thread_id 匹配 | 共同契约 |
| 能力及版本、参数摘要 | 摘要覆盖所有影响执行与权限的字段；规定确定性序列化，拒绝歧义 JSON | Agent24 授权，双方共享样例 |
| 有效期、授权范围 | 重试不能延长授权；规定时钟容差及批准后开跑前的再次检查 | Agent24 |
| 执行状态、run 关联 | 持久化请求键与 run；审批等待、拒绝、完成、失败、待核对分别表示 | Agent24 |
| 结果与回执 | 保存结果和待发记录；只允许匹配请求的对端回执更新状态 | Agent24 记账，Hyphae 投递 |
| 实际模型和用量 | provider/model/locality 与真实调用相符；估算与实际值有来源标识 | iDoris，Agent24 核对 |

Agent24 的 `version/intent/thread_id/reply_to/topic/payload/expires_at` 需要逐字段映射；未映射内容只供通信展示。`register/publish/inquire/subscribe` 本身均不构成执行授权；执行请求必须有独立判定条件。订阅通知不递归创建执行请求。

授权摘要还须说明重复 JSON key、数字表示、Unicode、空值与缺省值如何处理；只写“对参数做 hash”不足以让 Go、TypeScript、Rust 得到同一个值。错误码至少区分格式/版本不支持、过期、身份/目标不匹配、未授权、参数冲突、预算拒绝、模型不可用、执行失败和执行状态未知。传输失败单独记录，不能覆盖已完成的执行结果。

### 必须覆盖的执行状态与崩溃点

1. 收件通过格式验证后，Agent24 以发送者、目标和 request_id 登记；未授权不得启动 run。同键不同执行内容拒绝，同键同内容读取已有状态。
2. 等待审批可以持久化；批准后再次校验范围、有效期、预算和模块权限，再登记 run。注册、查询、普通文本和回执的 run 数必须为零。
3. run 开始后、结果落盘前崩溃，先按已登记 run 核对。只有确认未执行或执行器支持幂等，才允许重试；无法确认则进入待核对状态。
4. 结果与回执待发记录应能可靠恢复。结果已保存后，断线/重启只重发回执，不重做副作用。终态不能被迟到的“处理中”回执覆盖。

relay ACK、对端收件、批准执行和执行完成是不同事实。Hyphae 收件去重不替代执行登记；CLI 历史行数也不能替代副作用计数。

## 共享 fixtures 最低矩阵

| 类别 | 必须验证的结果 |
|---|---|
| 正常请求/回执 | 完整身份、能力版本、请求关联和结果一致；执行一次 |
| 文本、旧 F4、查询、通知、回执 | 可按兼容策略展示；执行零次 |
| 伪签名、错误目标、重复关键 tag、重复 JSON key | 拒绝；执行零次 |
| 未知版本/类型、过期、超限、截断 | 有确定错误；不降级执行 |
| 同请求重放、并发和重启 | 共享已有执行；同 ID 改参数被拒绝 |
| 执行前后故障 | 未开始可恢复；已开始但状态不明时核对；已完成只补回执 |
| 本地模型不可用、预算不足、越权模块 | 拒绝且无对应外部调用/副作用 |
| 重复/乱序回执、双端自动回复 | 终态不回退，无执行循环 |

每个 fixture 记录适用版本、固定输入、预期错误或状态、负责校验的层。签名 fixture 只用公开的测试密钥，并明确禁止用于真实身份。实际语音设备、四仓执行和付款测试不能由静态样例代替。
